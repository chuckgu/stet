# Stet v0.2 스펙 1: 영향 측정 (섀도)

작성: 2026-11-16 · 상태: 초안, 승인 전 · 상위 문서: concept-v0.2.md 9장의 1번 단계

## 1. 목표와 비목표

**왜 하는가.** hoop 같은 경쟁 제품은 문장의 모양만 보고 위험을 추측한다. 같은 `DELETE`가 3행을 지우는지 300만 행을 지우는지 모른다. Stet은 쓰기를 보내기 전에 DB를 읽는 구조가 이미 있으므로, 추측하지 않고 DB에 물어본다. 이것이 v0.2 네 단 중 첫째다. 그리고 다음 단계(enforce)의 전제다. 영향 측정 없이 enforce를 켜면 다중 행 쓰기를 전부 거부하거나 전부 통과시킬 수밖에 없다.

**목표**

- 게이트 대상 테이블에 대한 다중 행 쓰기가 몇 행에 걸리는지를 실행 전에 DB에 물어서 기록한다.
- 그 숫자와 테이블별 한도로 결정론적 verdict를 낸다. 모델은 부르지 않는다.
- 실행 뒤의 실제 행 수를 함께 기록해, 측정이 실제 트래픽에서 얼마나 맞는지 enforce 전에 알 수 있게 한다.
- 섀도 모드에서만 동작한다. 원래 쓰기는 바뀌지 않는다(규칙 6).

**비목표 (이 단계)**

- 쓰기를 막는 것 (2번 단계)
- 다중 행 쓰기를 행마다 값 단위로 판단하는 것
- 쓰기 전 값을 저장하는 것 (4번 단계)
- 외래 키 연쇄로 번지는 행 수를 세는 것. 어느 테이블로 번지는지만 기록한다
- 게이트 대상 테이블의 DDL·`TRUNCATE`를 금지 형태로 분류하는 것. 막을 수 있어야 의미가 있으므로 2번 단계로 옮긴다
- 실험 도구(`internal/lab`) 변경. lab 설정에 `impact`를 넣지 않으므로 녹화와 채점은 그대로다

## 2. 접근

측정 방법 셋을 일회용 Postgres 14(20만 행 테이블)로 비교했다. 한도는 100행으로 뒀다.

| 조건 | 실제 행 수 | 플래너 추정 | 한도까지만 세기 |
|---|---|---|---|
| PK 등호 | 1 | 1 | |
| 범위 | 99 | 101 | 99 (0.5ms) |
| 그룹 | 4,000 | 3,847 | 101에서 멈춤 (0.3ms) |
| `WHERE` 없음 | 200,000 | 200,000 | |
| 인덱스 없는 계산식 | 28,000 | 1,000 | 101에서 멈춤 (0.1ms) |
| 인덱스 없고 0행 | 0 | | 0 (6.3ms, 테이블 전체를 훑음) |

추정은 모두 0.1~0.4ms였고, 바인딩 값이 있는 문장에서도 동작했다.

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 추정만 (`EXPLAIN`) | 조인·서브쿼리를 포함해 모든 모양에 통한다. 가장 빠르다. 문장을 실행하지 않는다 | 플래너가 모르는 조건에서 크게 빗나간다. 28,000행을 1,000행으로 봤다 |
| B. 한도까지 세기 | "한도를 넘는가"에 정확히 답한다. 많이 걸릴수록 빨리 끝난다 | 조건절을 그대로 옮길 수 있는 단순한 모양만 된다. 적게 걸리고 인덱스가 없으면 테이블을 훑는다. 에이전트가 쓴 조건식을 실행하게 된다 |
| C. 실제로 실행하고 되돌리기 | 가장 정확하다. 외래 키 연쇄와 트리거까지 본다 | 쓰기를 두 번 실행하고 잠금을 잡는다. 섀도 모드의 약속과 부딪힌다 |

**선택: B를 우선하고 A로 보조한다.** 셀 수 있는 모양은 세고, 셀 수 없는 모양이나 시간 제한에 걸린 경우는 추정을 쓰되 불확실하다고 표시한다. C는 하지 않는다. 섀도 모드에서는 실제 행 수를 함께 기록하므로, 추정과 세기가 얼마나 맞는지는 실제 트래픽이 알려 준다.

## 3. 대상 문장

지금 `unsupported`로 빠지는 쓰기 가운데, 여러 행에 걸릴 수 있다는 것이 유일한 문제인 것만 측정 대상으로 바꾼다. 분류 이름은 `measured`다.

**측정 대상이 되는 조건.** 다음을 모두 만족해야 한다.

1. Query 또는 Parse 메시지에 문장이 하나이고, 최상위가 게이트 대상 테이블에 대한 `INSERT`, `UPDATE`, `DELETE`다.
2. 문장 전체에서 게이트 대상 테이블에 쓰는 곳이 그 최상위 하나뿐이다. `WITH` 안에서 게이트 대상 테이블을 또 고치는 문장은 대상이 아니다.
3. 값을 읽을 수 없어서 미지원인 형태가 하나도 없다: `on_conflict`, `multi_assign`, `indirection`.
4. 단일 행 쓰기가 아니다.
   - `UPDATE`·`DELETE`: `WHERE`에 PK 등호가 없다(지금의 `pkEquality`가 실패한다).
   - `INSERT`: `VALUES` 목록이 둘 이상이거나 `INSERT ... SELECT`다.

**측정 방법.**

| 형태 | 방법 |
|---|---|
| `UPDATE`·`DELETE`이고 `FROM`·`USING`·`WITH`·서브쿼리가 없으며, 조건식의 함수 호출이 모두 허용 목록 안에 있다 (4장) | 세기 (`count`) |
| `INSERT ... VALUES (...), (...)`이고 `WITH`·서브쿼리가 없다 | 문장에서 읽기 (`syntax`): `VALUES` 목록의 수 |
| 그 밖의 측정 대상 (조인, 서브쿼리, `WITH`, `INSERT ... SELECT`, 허용 목록 밖의 함수) | 추정 (`estimate`) |

**바뀌지 않는 것.**

- 기록되는 reason은 지금과 같다. 분류기는 지금의 검사 순서로 reason을 정하고(`not_single_row`, `join`, `subquery`, `with`, `multi_row`, `insert_select` 등), 측정 자격은 위 네 조건을 모두 본 뒤에 따로 정한다. 테이블에 `impact` 설정이 없거나 측정에 실패하면 게이트는 그 reason으로 지금과 똑같이 `unsupported`를 기록한다.
- 단일 행 쓰기는 측정하지 않는다. 판단할 수 있으면 지금처럼 값 단위 판단을 받고, 값을 읽을 수 없는 형태면 지금처럼 `unsupported`다. 예를 들어 `UPDATE ... SET x = (SELECT ...) WHERE id = 1`은 `subquery`로 남는다. 측정 대상으로 돌리면 영향이 1행이라 한도 안에 들어가 버리고, 값 단위 판단을 건너뛰게 된다.
- 다중 행 upsert(`INSERT ... VALUES (...), (...) ON CONFLICT ...`)는 지금처럼 `multi_row`로 기록되고 측정하지 않는다(조건 3).
- `copy`, `truncate`, `merge`, `nested_write`, `multi_statement`는 그대로다.

## 4. 측정

**시점.** 게이트의 `Begin`, 쓰기 메시지를 업스트림에 보내기 직전이다. 클라이언트는 이 동안 기다린다. 기존 상태 조립 예산(500ms) 안에서 돈다.

**트랜잭션 안에서는 측정하지 않는다.** 쓰기가 들어온 시점에 세션이 이미 명시적 트랜잭션 안이면(직전 ReadyForQuery 상태가 `I`가 아니면) 측정을 건너뛴다. 그런 쓰기의 verdict는 어차피 `in_transaction`이고, Stet의 연결에서는 그 세션의 미커밋 변경이 보이지 않으며, 자동 커밋을 쓰지 않는 드라이버에서는 모든 쓰기가 여기에 해당해 대기만 늘어난다. 프록시가 이 상태를 `Begin`에 넘겨 준다. 한 Sync 안에 Execute가 여럿인 암묵적 트랜잭션은 `Begin` 시점에 알 수 없으므로 측정은 하고, verdict만 `in_transaction`이 된다.

**연결.** Stet 자신의 연결 풀을 쓴다. 측정 하나는 트랜잭션 하나다.

```sql
BEGIN READ ONLY;
SET LOCAL ROLE "<클라이언트의 접속 계정>";
SET LOCAL statement_timeout = '200ms';
-- 추정, 그리고 셀 수 있으면 세기
ROLLBACK;
```

**권한과 안전.** 에이전트가 쓴 SQL은 신뢰하지 않는 입력이다(규칙 5). 일회용 DB로 확인한 것은 다음과 같다.

- 클라이언트의 접속 계정(`SessionInfo.User`)으로 역할을 바꾸면 그 역할의 권한과 행 수준 보안(RLS)이 적용된다. 권한이 없는 테이블은 `permission denied`가 난다.
- 읽기 전용 트랜잭션에서는 조건식 안에서 `INSERT`를 하는 함수가 거부된다. `pg_sleep(2)`는 `statement_timeout`으로 끊긴다.
- **그러나 `SET LOCAL ROLE`은 보안 경계가 아니다.** 내장 함수만으로 뚫린다. 조건식에 `set_config('role', 'none', true)`와 `query_to_xml('select ...', ...)`를 넣자, 세기 질의 안에서 역할이 Stet의 계정으로 돌아가고 그 권한으로 질의가 실행됐다.

그래서 다음과 같이 한다.

- **세기는 조건식의 함수 호출이 모두 허용 목록 안에 있을 때만 한다.** 그 밖에는 조건식을 실행하지 않는 추정만 쓴다.
  - 허용 목록은 세션 상태를 바꾸지 않고 SQL을 실행하지 않는 내장 함수로 좁게 시작한다(`now`, `lower`, `upper`, `length`, `date_trunc`, `abs` 정도). 구체적인 목록은 만드는 사람이 정하되 이 기준을 지킨다.
  - 스키마를 붙인 함수 호출과 `OPERATOR(...)` 문법이 있으면 세지 않는다.
- 추정은 문장을 실행하지 않는다. 플래너가 계획 단계에서 미리 계산하는 것은 immutable·stable 함수뿐이고, `set_config`와 `query_to_xml`은 volatile이라 계획 단계에서 실행되지 않는다(확인함).
- `SET LOCAL ROLE`과 읽기 전용은 그대로 둔다. 경계로 믿어서가 아니라, 에이전트가 실제로 건드릴 수 있는 행만 세기 위해서다.
- 남는 위험: 에이전트 역할이 함수·연산자·타입을 만들 수 있으면, immutable로 표시한 사용자 정의 함수가 추정의 계획 단계에서 Stet 연결 위에서 실행될 수 있다. 에이전트 역할에 `CREATE` 권한이 없다는 것이 전제다(spec-v0.1 10장). Stet의 upstream 계정은 필요한 권한만 갖는다.
- 운영 요구: Stet의 upstream 계정이 에이전트 역할의 멤버여야 한다(`GRANT agent_x TO stet`). 아니면 `SET ROLE`이 실패하고 그 쓰기는 측정 실패로 기록된다. 역할을 바꾸지 않고 다시 시도하지 않는다.

**세기 (`count`).**

```sql
SELECT count(*) FROM (SELECT 1 FROM <문장에 쓰인 테이블 참조> WHERE <문장의 WHERE> LIMIT <cap>) s
```

- `cap`은 `max_rows + 1`이다. 결과가 `cap`이면 "한도를 넘는다, 정확한 수는 모른다"이다(`capped: true`).
- 테이블 참조는 문장에 쓰인 그대로 옮긴다(스키마, `ONLY`, 별칭 포함). `WHERE`가 없으면 `WHERE` 없이 센다.
- 안쪽 `SELECT`는 문자열을 자르지 않고 파스 트리에서 만든다.
- 세기에 `statement_timeout`이 걸리면 추정값을 쓴다.

**추정 (`estimate`).** `EXPLAIN (FORMAT JSON) <원래 문장>`을 같은 바인딩 값으로 실행한다. 계획의 최상위 노드가 대상 문장의 `ModifyTable`이다. 그 자식 가운데 `Parent Relationship`이 `InitPlan`·`SubPlan`이 아닌 노드들의 `Plan Rows`를 더한다. `WITH` 안에서 게이트 대상이 아닌 테이블을 고치는 문장의 계획은 `InitPlan`으로 붙으므로 더해지지 않는다(확인함).

- 세기를 하는 쓰기에도 추정을 함께 실행해 기록한다. 0.1ms 수준이고, 추정이 얼마나 맞는지 볼 자료가 된다.

**매개변수 타입.** 세기 질의는 원래 문장의 `WHERE`만 옮기므로 `$1`이 안 쓰이고 `$2`만 쓰이는 경우가 생긴다. 타입 없이 보내면 Postgres가 `could not determine data type of parameter $1`(42P18)로 거부한다. 원래 문장을 Stet 연결에서 준비(Prepare)해 서버가 추론한 타입을 얻고, 그 타입을 세기·추정 질의에 준다. 값은 지금 `paramTexts`가 만드는 텍스트 값을 쓴다. 이 방식이 동작하는 것을 확인했다.

**테이블 크기.** `pg_class.reltuples`를 읽는다. 0보다 크면 `share = rows ÷ reltuples`를 계산한다. 아니면(한 번도 분석되지 않은 테이블) `share`는 비운다.

**외래 키 연쇄.** `DELETE`일 때만, 대상 테이블을 참조하면서 삭제 시 동작이 `CASCADE`·`SET NULL`·`SET DEFAULT`인 외래 키를 `pg_constraint`에서 찾아 `[{table, on_delete}]`로 기록한다. 번지는 행 수는 세지 않는다.

**실제 행 수.** 프록시가 그 쓰기의 CommandComplete 태그(`UPDATE 48211`, `DELETE 3`, `INSERT 0 5`)에서 행 수를 읽어 `Outcome`에 실어 준다. 한 Sync 안에 Execute가 여럿이면 그 쓰기의 순번에 해당하는 태그를 쓴다. 감시 중인 쓰기가 없는 단위에서는 태그를 해석하지 않는다.

## 5. 판정

**설정.** 테이블별로 켠다. `impact`가 없는 테이블은 지금과 완전히 같다.

```yaml
tables:
  contacts:
    # ...
    impact:                  # 없으면 다중 행 쓰기는 지금처럼 unsupported
      max_rows: 100          # 필수. 이보다 많이 걸리면 hold
      max_share: 0.1         # 선택. UPDATE·DELETE가 테이블의 10%를 넘게 걸리면 hold
```

- `max_rows`는 필수이고 1 이상의 정수다. `max_share`는 선택이고 0 초과 1 이하다.
- `max_share`는 `UPDATE`와 `DELETE`에만 적용한다. 있는 행 가운데 얼마를 건드리느냐를 보는 값이라 `INSERT`에는 뜻이 없다. 작은 테이블을 지키는 용도다. 50행짜리 테이블에서 40행을 지우는 쓰기는 `max_rows: 100` 안이지만 80%다.
- 기본으로 켜지 않는 이유: 기존 설정과 실험 녹화의 동작이 바뀌면 안 된다.

**순서.** 위에서부터 처음 걸리는 것을 적용한다. 앞의 두 줄은 지금의 동작 그대로다.

| # | 조건 | verdict | reason |
|---|---|---|---|
| 1 | 미지원 형태. 측정 대상이지만 테이블에 `impact` 설정이 없는 경우를 포함한다 | `unsupported` | 지금의 reason |
| 2 | 트랜잭션 안의 쓰기 | `unsupported` | `in_transaction` |
| 3 | 측정에 실패했다 | `unsupported` | 지금의 reason. 실패 원인은 `impact.error`에 남는다 |
| 4 | 행 수가 `max_rows`를 넘는다 (`capped` 포함) | `hold` | `impact:rows` |
| 5 | `UPDATE`·`DELETE`의 비율이 `max_share`를 넘는다 | `hold` | `impact:share` |
| 6 | 한도 안이지만 방법이 추정뿐이다 | `escalate` | `impact:uncertain` |
| 7 | 한도 안이고 방법이 세기 또는 문장에서 읽기다 | `commit` | |

- 6번을 `commit`이 아니라 `escalate`로 둔다. 추정이 28배 낮게 나온 실측이 있어서다. 섀도 데이터에서 추정이 얼마나 맞는지 본 뒤에 다시 정한다.
- 숫자는 reason에 넣지 않고 `impact` 컬럼에 둔다.
- 이 판정은 `internal/decide`에 둔다. 모델 호출이 없고 어댑터와 무관하다(규칙 7).

## 6. 기록

`stet.decisions`에 `impact jsonb` 컬럼을 추가한다. 측정하지 않은 쓰기는 NULL이다. 측정 대상이 아닌 쓰기, `impact` 설정이 없는 테이블의 쓰기, 트랜잭션 안이라 건너뛴 쓰기가 여기에 해당한다.

```json
{
  "method": "count",
  "rows": 99,
  "capped": false,
  "cap": 101,
  "estimate": 101,
  "table_rows": 200000,
  "share": 0.000495,
  "cascades": [{"table": "deals", "on_delete": "cascade"}],
  "actual_rows": 99,
  "measure_ms": 1,
  "error": null
}
```

- `method`는 `count`, `estimate`, `syntax` 중 하나다. 측정에 실패하면 `method`는 비고 `error`에 원인이 들어간다.
- `rows`는 판정에 쓴 값이다. `estimate`는 추정을 실행했을 때의 추정값이다.
- `actual_rows`는 실행되지 않은 쓰기에서는 비어 있다.
- 스키마는 `internal/store/schema.sql`에 `ALTER TABLE stet.decisions ADD COLUMN IF NOT EXISTS impact jsonb`로 더한다. 이 파일은 시작할 때마다 실행되므로 여러 번 실행해도 안전해야 한다.
- 측정 대상 쓰기의 다른 컬럼: `target_pk`, `proposed`, `state`, `questions`, `answers`는 NULL이다. `latency_ms`는 측정 시간을 포함한다. 클라이언트가 실제로 기다린 시간이기 때문이다.
- 모델에 보내는 상태(`gate.State`)는 바꾸지 않는다. 필드 순서가 답을 바꾸므로(D19), 기존 녹화의 재생이 달라지면 안 된다.

## 8. 실패 처리

섀도 모드이므로 어떤 실패에서도 원래 쓰기는 그대로 통과한다.

| 상황 | 동작 |
|---|---|
| `SET ROLE` 실패 (Stet 계정이 그 역할의 멤버가 아님) | 측정 실패로 기록한다. 역할마다 한 번 경고 로그를 남긴다 |
| 세기가 200ms를 넘음 | 추정값을 쓴다 |
| 추정이 실패 (`WHERE CURRENT OF`, 임시 테이블, Stet 연결에서 준비되지 않는 문장) | 측정 실패로 기록한다 |
| 전체가 500ms를 넘음 | 측정 실패로 기록한다 |
| 바인딩 값을 텍스트로 바꾸지 못함 | 지금과 같다 (`state_error`) |

## 9. 지연과 부하

- 측정 한 번은 왕복 서너 번이다(트랜잭션 시작, 추정, 세기, 되돌리기). 로컬에서 1~2ms 수준으로 예상한다.
- 최악은 인덱스 없는 조건에 적게 걸리는 쓰기다. 테이블을 훑는데, 200ms에서 끊고 추정값을 쓴다. 원래 쓰기도 같은 스캔을 하므로 부하는 최대 두 배다.
- 게이트 대상이 아닌 문장의 경로는 바뀌지 않는다. `internal/proxy/latency_test.go`의 2ms 예산을 그대로 통과해야 한다.
- 섀도 모드의 약속(규칙 6)과의 관계: 문장은 바꾸지 않는다. 더해지는 것은 읽기 질의와 클라이언트의 대기이고, 지금의 상태 조립과 같은 종류다. 잡는 잠금은 읽기 잠금뿐이다.

## 10. 한계

- **다중 행 형태로 쓰면 값 단위 판단을 받지 않는다.** `WHERE id IN (5)`는 한 행만 건드리지만 측정 대상으로 분류되어 영향 판정만 받는다. 섀도에서는 기록의 문제지만, enforce에서는 판단을 피하는 길이 된다. 2번 단계 설계에서 닫는다.
- 다중 행 쓰기는 `recent_changes`에 들어가지 않는다. PK가 없어서다. 그 뒤에 같은 행을 고치는 단일 행 쓰기의 conflict 질문은 그 변경을 보지 못한다.
- 외래 키로 번지는 행 수와 트리거가 하는 쓰기는 세지 않는다.
- 추정은 통계에 달려 있다. 2장의 표처럼 크게 빗나갈 수 있다.
- 허용 목록 밖의 함수를 쓰는 조건식은 세지 못하고 추정만 받는다. 그래서 한도 안이어도 `escalate`가 된다.
- 에이전트 역할이 함수를 만들 수 있으면 추정의 계획 단계가 공격 통로가 될 수 있다(4장).
- Stet 연결의 `search_path`는 클라이언트 세션과 다를 수 있다. 스키마 없는 이름은 다른 테이블로 풀릴 수 있다. 지금의 현재 행 조회에도 있는 한계다.

## 11. 수용 기준

- [ ] 3장의 네 조건을 만족하는 문장이 `measured`로 분류되고, 방법과 지금의 reason이 함께 나온다.
- [ ] 다음은 `measured`가 되지 않고 지금의 reason으로 남는다: 단일 행 쓰기에 서브쿼리·`WITH`·조인이 붙은 것, 다중 행 upsert, `WITH` 안에서 게이트 대상 테이블을 또 고치는 문장.
- [ ] `impact` 설정이 없는 테이블의 기록은 이 변경 전과 같다. 기존 테스트가 고치지 않고 통과한다.
- [ ] 세기: 한도 이하는 정확한 수, 초과는 `capped`. 텍스트·바이너리 바인딩 값, 안 쓰이는 매개변수, 별칭, `ONLY`, 스키마 한정 이름에서 동작한다.
- [ ] 조건식에 허용 목록 밖의 함수(`set_config`, `query_to_xml`, 스키마를 붙인 함수)가 있으면 세지 않는다. Stet의 연결에서 그 함수가 실행되지 않는다.
- [ ] 추정: 조인, 서브쿼리, `WITH`, `INSERT ... SELECT`에서 동작한다. `WITH` 안에 다른 테이블을 고치는 문장이 있어도 대상 문장의 행 수만 나온다.
- [ ] 측정은 클라이언트의 역할로, 읽기 전용으로 실행된다. 멤버가 아니면 측정 실패로 기록된다.
- [ ] 명시적 트랜잭션 안의 쓰기는 측정하지 않고 `impact`가 NULL이다.
- [ ] 5장의 표대로 verdict와 reason이 나온다. `max_share`는 `INSERT`에 적용되지 않는다.
- [ ] 실제 행 수가 Simple Query, Extended Query, 한 Sync에 Execute가 여럿인 경우에 맞게 기록된다.
- [ ] 측정 대상 쓰기가 실패하거나 측정이 실패해도 원래 쓰기의 결과는 직접 연결했을 때와 같다. 기존 프로토콜 테스트 전체를 `impact`를 켠 게이트로 다시 돌려 확인한다.
- [ ] `STET_TEST_PG`를 설정한 `go test -race ./...`와 2ms 지연 예산을 통과한다.

## 12. 정한 것과 남긴 것

**이 문서에서 정한 것** (설계자의 판단. 사용자가 고른 것은 "세기 우선, 추정 보조"다)

- 테이블별 opt-in. 기본으로 켜지 않는다.
- `max_rows`는 필수, `max_share`는 선택이고 `UPDATE`·`DELETE`에만 적용.
- 추정뿐이면서 한도 안이면 `escalate`.
- 세기의 시간 제한 200ms.
- 세기는 조건식의 함수 호출이 허용 목록 안에 있을 때만. `SET LOCAL ROLE`은 경계로 믿지 않는다.
- 명시적 트랜잭션 안의 쓰기는 측정하지 않는다.
- 측정 자격은 3장의 네 조건으로 정하고, 기록되는 reason은 지금의 검사 순서를 그대로 쓴다.
- 판정 순서에서 형태가 트랜잭션보다 먼저다(지금의 동작).
- 외래 키 연쇄는 테이블 목록만 기록.
- DDL·`TRUNCATE` 금지 형태 분류는 2번 단계로 이동.
- `measured` 쓰기의 `proposed`는 기록하지 않음.

**만드는 사람에게 남긴 것**

- 내부 타입과 함수 이름, 파일 배치.
- 파스 트리에서 안쪽 `SELECT`를 만드는 구체적 방법.
- 함수 허용 목록의 구체적 항목(4장의 기준 안에서).
- 외래 키 조회와 테이블 크기 조회를 캐시할지 여부.
- 테스트의 구성.
