# Stet 컨셉 v0.2: 상태를 아는 에이전틱 쿼리 통제

작성: 2026-11-16 · 상태: 방향 확정, 단계별 설계 전 · 이전 버전: v0.1 (spec-v0.1.md)

이 문서는 v0.1 실험 뒤에 방향을 다시 잡은 논의를 정리한 것이다. 무엇을 만들지, 왜 그렇게 바꾸는지, 어떤 순서로 가는지를 담는다. 단계별 설계는 따로 쓴다. 결정 자체는 decisions.md D29, D30, D31에 있다.

## 1. 정의와 역할

> 기업이 데이터 업무를 에이전트에게 맡기면서도 통제권을 잃지 않게 한다. 에이전트가 데이터에 보내는 질의의 길목에 서서, 문장을 보고 추측하지 않고 DB에 물어보고 판단하고, 그 근거를 사람의 감독에 그대로 잇는다.

- **목적은 위임이다**(D31). 맡기는 일이 늘수록 사람이 직접 확인하는 일은 줄어든다. 빠진 확인을 실행 시점의 통제와 사람이 감독할 수 있는 체계로 다시 세운다(2장).
- **방식은 DB에 물어보는 것이다.** 즉시 판단과 사람의 감독이 같은 근거를 쓴다. 사람에게 올릴 때 "위험: 높음"이 아니라 "48,211행, 테이블의 24%, `deals`로 번진다"를 보여 준다. 같은 자리의 다른 제품과 갈리는 곳이다(6장).
- **맡는 분야는 에이전틱 쿼리 통제다**(D30). 에이전틱 쿼리는 에이전트가 실행 시점에 스스로 만들어 데이터 시스템에 보내는 읽기와 쓰기다. 사람이 미리 쓰고 검토한 코드의 질의와 달리, 아무도 보지 않은 채 실행된다. 에이전트를 운영에 붙이는 회사는 이 질의의 가드레일과 거버넌스를 어디에 둘지 정해야 하고, Stet은 그 자리를 맡는다.
- 보내는 쪽을 가리지 않는다. 실수하는 에이전트, 지시를 주입당한 에이전트, 공격에 쓰이는 에이전트의 질의가 같은 길목을 지나고 같은 통제를 받는다(7장).
- 첫 제품의 범위는 그대로다. Postgres 하나, 쓰기부터, 깊이 먼저다. 읽기는 기록부터 시작한다(9장). 다른 데이터 플랫폼과 품질 계층은 목적지다(12장).
- v0.1의 전제("클라이언트가 틀릴 수 있다고 가정하는 DB")는 그대로다.
- 바뀌는 것은 무게중심이다. v0.1은 판단 모델이 쓰기를 판단하는 것이 중심이었다. v0.2는 결정론으로 볼 수 있는 것을 먼저 다 보고, 남는 것만 모델에 묻는다.
- 대상은 에이전트의 호출이다. 대용량 서비스 트래픽에는 붙지 않는다(5장).

**세 역할**

| 역할 | 책임 |
|---|---|
| 결정론적 통제 | 권한, 영향 한도, 금지 형태처럼 넘을 수 없는 경계를 강제한다 |
| 판단 모델 | 데이터 상태와 정책을 놓고 뜻을 봐야 하는 것을 판단한다. 확신하지 못하면 그렇다고 알린다 |
| 사람 | 위임 범위와 정책을 정한다. 예외와 결과를 보고 정책을 고친다. 멈추고, 되돌리고, 위임을 거둔다 |

- 실행 순서는 그대로다. 결정론이 먼저 보고, 남는 것만 모델에 묻는다.
- 판단 모델이 하는 일은 사람이 반복하던 맥락 판단을 대신해서, 자동으로 처리할 수 있는 범위를 넓히는 것이다. 규칙 코드는 규칙 경계 근처의 정상 쓰기 31.2%를 막았고 판단 모델은 2.5%를 막았다(lab.md "hard negative 비교").
- DB는 지금 상태를 알려 주지만 업무의 목적은 알려 주지 않는다. 그래서 판단에는 "누가 정한 어떤 정책인가"가 함께 남아야 한다. 지금은 정책이 설정 파일에 있고 판단 기록에 그 해시(`policy_version`)가 남는다. 누가 바꿨는지는 Stet의 기록에 없다.

**사람이 하는 일**

```
 policy ──> automatic judgment ──> review of exceptions ──> policy change
   ▲          and enforcement          and outcomes               │
   └──────────────────────────────────────────────────────────────┘
```

- 평소에는 사람이 정한 정책과 한도 안에서 자동으로 처리한다.
- 불확실하거나 영향이 큰 건은 근거와 함께 사람에게 올린다.
- 사람은 올라온 건을 처리하고, 쌓인 결과를 보고 정책을 고치고, 필요하면 멈추거나 되돌린다.
- 질의마다 승인 버튼을 누르는 구조가 아니다. 그 구조는 규모를 따라가지 못한다(4장).

## 2. 왜 바꾸는가: v0.1 실험에서 배운 것

실험 전에 고정한 기준으로는 go였다(lab.md). 하지만 그 기준은 "어느 게이트가 나은가"를 쟀고, "게이트가 필요한가"는 재지 않았다. 결함을 유형별 100건씩 주입했기 때문에 에이전트가 실제로 얼마나 틀리는지는 판정에 들어가지 않았다. 필요성 쪽으로 다시 읽으면 불리한 숫자가 셋 있다.

| 관찰 | 숫자 | 뜻 |
|---|---|---|
| Opus 5.5 에이전트는 함정을 대부분 스스로 피했다 | 함정 326개 중 결함 쓰기 14건, 모두 근접 중복(F1). 낡은 직함·열린 딜 모순·심은 지시 함정 199개에서는 0건 | 쓰기 전에 DB를 읽는 에이전트는 읽는 시점에 보이는 모순을 피한다 |
| 규칙을 코드로 옮긴 A1이 F2~F4를 모두 잡았다 | A1 recall 96%. 모델(C)이 이긴 곳은 중복(95% 대 84%)과 false hold(1.1% 대 4.6%) | "판단 모델이 규칙 코드보다 낫다"는 중복 탐지와 덜 막는 것 말고는 확인되지 않았다 (D28이 다시 본다) |
| 저가 LLM도 임계값을 맞추면 품질이 가깝다 | Haiku 5.5: 등록 임계값 66.7%, 0.6으로 낮추면 97.1% (결과를 본 뒤 고른 값) | Jev의 우위는 품질이 아니라 비용과 지연이다 |

여기에 방향성 문제가 더해진다. 모델은 계속 좋아지므로 "에이전트의 판단 실수를 잡는다"에만 건 제품은 시간이 갈수록 가치가 줄어든다. 하지만 한 건이 틀릴 확률이 낮아진다고 통제의 필요가 줄어드는 것은 아니다. 필요는 대략 다음 넷의 곱이다.

```
맡긴 일의 양 × 한 건이 틀릴 확률 × 한 건이 건드리는 범위 × 아무도 확인하지 않을 확률
```

- 모델이 좋아지면 둘째가 줄어든다.
- 모델이 좋아지면 회사는 더 많이, 더 넓은 권한으로 맡기고 덜 확인한다. 첫째, 셋째, 넷째가 커진다.
- 어느 쪽이 이기는지는 재지 않았다. 그래서 가설로 둔다.

**전략 가설**(D31)

> 기업은 효율을 위해 데이터 업무를 에이전트에게 더 많이 맡긴다. 직접 확인이 줄어드는 만큼, 실행 시점의 판단·통제와 사람의 감독을 잇는 체계가 필요해진다.

- 이 가설에서는 모델이 좋아지는 것이 역풍이 아니라 순풍이다. 좋아질수록 더 맡기기 때문이다.
- v0.1 실험은 판단 엔진의 성능을 잰 것이다. 이 가설을 증명하지도 반박하지도 않았다.
- 틀렸다고 볼 조건:
  - 회사가 에이전트에게 운영 데이터의 쓰기를 맡기지 않는다. 읽기만 맡기고 쓰기는 사람이 실행한다.
  - 맡기더라도 사람의 확인이 줄지 않는다.
  - 위임이 DB 길목을 지나지 않는다. 에이전트가 앱 API만 쓰고, 그 앱이 서비스 계정으로 붙는다(5장).
  - DB 업체나 에이전트 프레임워크가 같은 통제와 감독을 기본으로 준다.
- 실험으로는 확인할 수 없다. 고객 대화에서 확인한다.

가설과 별개로, 모델이 좋아져도 줄지 않는 것이 둘 있다. 가설이 약해져도 남는 근거다.

- 에이전트가 아무리 똑똑해도 알 수 없는 것: 다른 에이전트의 동시 쓰기, 읽은 뒤에 바뀐 행.
- 맞게 썼더라도 남겨야 하는 것: 누가, 누구를 대신해, 무엇을 보고 썼는지.

낡은 쓰기는 첫째의 대표 사례다. 얼마나 자주 나는지는 아무도 재지 않았으므로(11장), 그 빈도에 제품 전체의 필요성을 걸지 않는다.

## 3. 데이터와 에이전트 사이의 갭

전통적 DB는 클라이언트에 대해 여러 가정을 하고, 에이전트는 그 가정을 각각 다르게 깬다. 온톨로지는 그중 앞의 둘만 메운다.

| 갭 | 어긋나는 것 | 지금 메우는 쪽 | 에이전트가 늘면 |
|---|---|---|---|
| 의미 | 스키마는 형식만 말한다 | 온톨로지·시맨틱 레이어: Fabric IQ, Databricks, Snowflake, Palantir, dbt. 오픈소스로 Semantica, NVIDIA Auto Ontology | 줄어든다. 모델이 스키마를 더 잘 읽고 온톨로지도 자동으로 만든다 |
| 행동 단위 | DB는 행 단위 쓰기를 주는데 업무는 행동 단위다 | Palantir Action, MCP 도구, 앱 API | 앱 계층의 일로 남는다 |
| 권한·폭발 반경 | 자격 증명이 작업보다 넓다 | 접근 통제 프록시(hoop, Aegis), 승인 게이트(Bytebase), 브랜칭(Neon, Xata) | 사고가 요란해서 플랫폼 기본값으로 빨리 닫힌다 |
| 시간 | 트랜잭션은 밀리초 단위의 판단을 가정한다. 에이전트는 읽고 수 초~수 분 뒤에 트랜잭션 밖에서 쓴다 | 2026년 논문 다섯 편. 제품은 찾지 못했다 | 커진다. 쓰기량과 작업 길이에 비례한다 |
| 쓰기의 의미적 옳음 | 제약은 형식만 본다 | Stet v0.1 | 줄어든다 (2장) |
| 책임·되돌리기 | DB 로그는 역할과 행만 안다. 그 에이전트가 쓴 것만 되돌리는 방법이 없다 | 백업 업체(Rubrik, Commvault)가 스냅샷 단위로 | 커진다. 건마다의 사람 승인이 줄수록 사후 복구의 비중이 커진다. 사전 한도, 예외 개입, 위임 철회와 함께 쓴다 |

- 이름 붙은 레이어 중에 완전히 빈 곳은 없다. 비어 있는 것은 층이 아니라 기록 하나다: 어느 에이전트 세션이 어떤 버전을 읽고 무엇을 썼는가.
- 이 기록 하나에서 낡은 쓰기 탐지, 행 단위 되돌리기, 읽는 쪽에 주는 출처 표시가 함께 나온다.
- 근거는 대부분 벤더 글과 프리프린트다. 수치는 방향 정도로만 본다. "틀린 데이터를 썼다"는 공개 사고 사례는 찾지 못했다. 검색된 사고는 모두 삭제·파괴였다.

## 4. 예측

아직 겪지 못한 사람이 많다. 그래서 지금의 경험만이 아니라 추세도 근거로 쓴다.

| 추세 | 숫자 | 뜻 |
|---|---|---|
| 에이전트 수 | 운영 중인 기업의 평균 활성 에이전트 5개(2025-02) → 13개(2026-04). 그중 절반은 서로 격리되어 돈다 (Salesforce) | 아직은 같은 데이터를 함께 만지는 경우가 적다 |
| 작업 길이 | 혼자 끝내는 작업 길이 약 50분(2025 초) → 14시간대(2026 초) (METR, 2차 출처) | 읽고 나서 쓰기까지의 간격이 벌어진다 |
| 사람 승인 | 권한 요청의 93%를 그대로 승인 (2차 출처) | 쓰기를 하나씩 보는 구조는 규모를 따라가지 못한다. Stet이 사람에게 올리는 건에도 똑같이 적용된다(7장) |

**낡은 쓰기가 될 확률**은 쓰기가 행에 고르게 퍼진다고 가정하면 대략 다음과 같다.

```
(시간당 쓰기 수 × 읽기~쓰기 간격) ÷ 행 수
```

- 지금 실험 규모(시간당 약 1,100건, 간격 15초 가정, 연락처 5,000개)에서는 0.1% 미만이다. 녹화 전체에서 기대값이 1건이 안 된다.
- 에이전트가 10배, 간격이 10배가 되면 약 10%다.
- 실제는 이보다 나쁘다. 같은 사건에 여러 에이전트가 동시에 반응하면 같은 행에 몰린다.

**이 예측이 틀리는 경우**

- 에이전트가 계속 격리된 채 서로 다른 데이터만 만진다.
- DB 업체가 세션 단위 추적을 기본 기능으로 넣는다.

## 5. 자리: 에이전트 전용 길목, DB 쪽

```
 services (high volume) ──────────────────> Postgres
 agents ───────────────> stet ────────────> Postgres
                           │
                           └──> judgment model, before the write
```

- **에이전트 호출에만 붙는다.** 서비스는 지금처럼 DB에 직접 붙는다. 그래서 지연 부담이 작다. 판단이 붙는 쓰기에 더해지는 시간은 p95 250ms 정도이고 에이전트의 한 스텝은 초 단위다. Stet이 죽어도 서비스는 영향을 받지 않는다.
- **DB 쪽에 선다.** DB와 같은 네트워크에서, 에이전트가 DB로 들어가는 유일한 길목이다. 이유는 셋이다.
  - 에이전트 PC에 두면 에이전트가 건너뛸 수 있다. 에이전트는 자기 머신에 있는 것을 다 읽는다.
  - 모든 에이전트를 한곳에서 봐야 에이전트 간 충돌과 낡은 쓰기를 판단할 수 있다.
  - 쓰기마다 DB에 물어보므로 DB에 가까워야 빠르다.
- **호출을 보고 에이전트인지 알아내지 않는다.** 에이전트용 자격 증명이 Stet을 거쳐야만 통하게 만든다.
  - 직접 운영하는 Postgres: 접속 규칙(`pg_hba.conf`)에 "에이전트 역할은 Stet의 주소에서 온 접속만 허용"을 적는다. 코드 변경이 없다.
  - 매니지드 Postgres: 역할별 접속 규칙을 못 쓰는 경우가 많다. 진짜 비밀번호는 Stet이 쥐고 에이전트에게는 Stet용 토큰만 준다. 새로 만들어야 한다.
  - 에이전트마다 DB 역할을 따로 주면 접속 계정이 곧 신원이다. `application_name`은 스스로 적는 값이라 신원이 아니다.
- **못 막는 경우**: 누군가 에이전트에게 서비스나 사람의 자격 증명을 그대로 주면 Stet은 그 쓰기를 보지 못한다. 배치와 무관하게 같다. "에이전트에게는 에이전트용 역할만 준다"는 운영 규칙이 전제다.
- **운영 규칙은 회사의 거버넌스가 정한다**(D31). Stet이 대신 정할 수 없다. 규칙은 둘이다.
  - 에이전트에게는 에이전트용 역할만 준다.
  - 에이전트의 요청을 받아 질의를 실행하는 서비스(MCP 서버, 도구 백엔드)도 에이전트용 역할로 Stet을 거쳐 붙는다. 이 경우 문장 모양은 사람이 미리 쓴 것이고 값만 에이전트가 고른다. 값 단위 판단과 영향 한도는 그대로 적용된다.
- Stet은 규칙이 지켜지는지를 보여 줄 수 있다. 게이트 대상 테이블에 Stet을 거치지 않고 쓰는 접속이 있는지를 DB에 물어 보고하는 것이다. 방법은 설계하지 않았다(11장).
- **지금 코드와의 차이**: 지금은 "누가 쓰느냐"가 아니라 "어느 테이블에 쓰느냐"로 대상을 고른다.
- 에이전트 쪽에는 맥락을 알려 주는 역할만 남는다(`on_behalf_of`, 작업 이름). 이 값들은 에이전트가 스스로 적는 값이다. 인증된 사실(접속 계정)과 구분해서 기록하고, 한도와 권한에는 쓰지 않는다(7장). 개발자 PC에서 로컬로 띄우는 것은 체험용이다.

## 6. 같은 자리의 경쟁자: hoop

저장소 `hoophq/hoop`을 2026-11-16에 직접 읽었다(커밋 `5afde26`). README와 `sidecar/analyzer` 중심으로 읽었고 전체를 본 것은 아니다.

**무엇인가**

- "Runtime control for agents". 에이전트와 자원 사이의 와이어에 서는 사이드카다. PostgreSQL, MSSQL, HTTP 등을 다룬다.
- 통제는 넷이다: 마스킹, 가드레일(순서 있는 거부 목록. 연산 종류·정규식·테이블), Session Analyzer(LLM이 문장 위험도를 low / medium / high로 분류), Reviews(사람 또는 모델 승인).
- 규칙이 먼저 돌고 그 뒤에 LLM이 돈다. README의 논지는 "정적 규칙은 의도를 판단하지 못하고, 사람은 기계 속도로 검토하지 못한다"이다.

**LLM을 쓰는 방법**

| 방법 | 모델이 도는 곳 | 데이터가 가는 곳 |
|---|---|---|
| 고객의 LLM 계정 (`anthropic`, `openai`, `gemini`, `vertex`) | 해당 클라우드 | 고객이 계약한 업체 |
| hoop 호스팅 모델 (`qwen3-4b`, 무료 티어 기본값) | hoop 서버 | hoop. 문장에 개인정보가 들어갈 수 있다고 README가 경고한다 |
| 고객이 직접 띄운 OpenAI 호환 서버 | 고객 인프라 | 밖으로 안 나간다. 모델 운영은 고객 몫이다 |

**상태**

- 제품은 젊다. 사이드카의 첫 커밋이 2026-08-27이고, 컨트롤 플레인의 승인 큐와 설정 UI는 아직 없다.
- 엔지니어링은 얇지 않다. 11주 동안 커밋 143개, 사이드카만 Go 6.8만 줄에 테스트 7.7만 줄이다. SQL 분류기는 데이터 변경 CTE, `DO` 블록, `EXPLAIN ANALYZE`를 다룬다.
- 오픈소스는 제한적이다. 저장소는 MIT지만 와이어 코덱은 비공개 모듈이라 소스로 빌드할 수 없고, 무료 빌드는 가드레일 규칙을 1개까지만 적용한다.

**구조적 한계**

- 공개된 코드에서 사이드카는 DB에 스스로 질의하지 않는다. 와이어를 지나가는 바이트만 본다.
- LLM은 문장 텍스트와 연산·테이블 이름만 받는다. 프롬프트는 "문장 자체만 판단하라"고 지시한다.
- 판정은 리터럴을 지운 문장 모양으로 캐시된다. `WHERE id = 1`과 `WHERE id = 2`는 같은 판정을 받는다.
- 그래서 같은 문장이 3행을 지우는지 300만 행을 지우는지 모르고, 중복 생성·낡은 값 덮어쓰기·다른 행에 달린 정책 위반을 볼 수 없다.
- LLM 비용 때문에 호출 상한(`max_calls`)과 속도 제한을 둔다. 실패 시 기본값은 통과(`fail_open: true`)다. 상한을 넘었을 때의 동작은 직접 돌려 확인하지 않았다.

**규칙+LLM 대 규칙+Jev**

비용·지연·품질은 우리 실험에서 같은 질문을 Claude에 물은 결과이고, hoop을 직접 잰 것이 아니다.

| 항목 | 규칙+LLM | 규칙+Jev | 유리한 쪽 |
|---|---|---|---|
| 1,000건당 비용 | Haiku $0.237, Opus $8.31 | $0.048 | Jev |
| p95 지연 | 3.0초, 5.4초 | 249ms | Jev |
| 쓰기마다 묻기 | 캐시와 호출 상한이 필요 | 상한 없이 가능 | Jev |
| 답의 형태 | 위험 등급 셋과 설명문 | 질문별 확률 (임계값 조정, 재채점 가능) | Jev |
| 막은 이유 | 자유 서술 | 구조화 (`duplicate:4812`, `policy:2`) | Jev |
| 열린 질문 ("이 문장이 위험한가") | 잘한다 | 맞지 않는다 | LLM |
| 최고 품질 | Opus recall 99.5%, false hold 0% | 97.6%, 1.1% | LLM |
| 자체 호스팅 | 고객이 운영하면 가능 | 불가, 외부 API | LLM |
| 한국어 | 한글↔로마자 중복 100% | 86% | LLM |

- Jev가 나은 구석은 "값 단위로, 쓰기마다 묻는 판단"이다. 좁지만 hoop이 구조상 못 가는 곳이다.
- 이 구석의 실제 경쟁자는 Opus가 아니라 소형 로컬 LLM이다. 품질과 지연은 아직 모른다. 녹화된 상태를 로컬 소형 모델에 재생하는 arm으로 잴 수 있다(11장).

## 7. 방향: 깊이로 경쟁한다

같은 자리에 hoop이 있다고 피하지 않는다. 이 레이어가 필수가 되면 여러 제품이 설 자리가 있고, 초기 경쟁자는 더 잘 만들면 된다.

막아야 할 위험은 세 종류다.

| 위험 | 내용 | 지금 맡는 쪽 |
|---|---|---|
| 유출 | 읽으면 안 되는 것을 읽는다 | hoop의 마스킹 |
| 파괴 | 지우거나 못 쓰게 만든다 | hoop의 가드레일과 승인 |
| 오염 | 권한도 있고 문장도 멀쩡한데 데이터가 틀려진다 | 비어 있다 |

hoop은 "이 문장이 위험한가"를 묻는다. Stet은 "이 쓰기 뒤에도 데이터가 맞는가"를 묻는다. hoop은 문장을 보고 추측하고, Stet은 DB에 물어본다. 그 위에 네 단을 쌓는다.

| 단 | 내용 | 모델 | 지금 |
|---|---|---|---|
| 1. 영향 측정 | 몇 행이 걸리는지, 테이블의 몇 %인지, 외래 키로 어디까지 번지는지를 DB에 묻고 그 숫자로 정한다 | 불필요 | 없음 |
| 2. 되돌릴 수 있게 하기 | 쓰기 전 값을 남긴다. 작은 쓰기는 막거나 승인받는 대신 통과시키고 되돌릴 수 있게 둔다 | 불필요 | 단일 행의 쓰기 전 값만 기록 |
| 3. 값 단위 판단 | 중복, 최근 변경 되돌리기, 정책 위반을 판단 모델에 묻는다 | Jev | 있음 (섀도) |
| 4. 낡은 쓰기 탐지 | 세션이 읽은 버전과 쓸 때의 버전을 비교한다 | 불필요 | xmin 기록만 |

- 2단은 "규칙만으로는 방해가 된다"에 대한 답이다. 막는 대신 되돌릴 수 있게 하면 정상 쓰기를 덜 막는다.
- Postgres 하나만 깊게 판다. 넓이는 뒤에 붙인다(9장).

**읽기에는 단마다 다르게 적용된다**

- 1단은 그대로 적용된다. 몇 행이 나가는지, 테이블의 몇 %인지를 잰다. 처음에는 기록만 한다.
- 2단은 적용되지 않는다. 읽어 간 것은 되돌릴 수 없다. 그래서 유출은 실행 전에 재서 막아야 한다.
- 4단의 재료다. 세션이 무엇을 읽었는지가 낡은 쓰기 탐지의 입력이다.
- 지금 코드는 읽기를 보지 않는다. 게이트 대상 테이블에 쓰지 않는 문장은 `pass`로 분류되어 그대로 넘어간다.

**보내는 쪽: 실수, 주입, 공격**

| 보내는 쪽 | 예 |
|---|---|
| 실수하는 에이전트 | 낡은 값으로 덮어쓴다. 조건을 빠뜨려 여러 행을 고친다 |
| 지시를 주입당한 에이전트 | 미팅 노트에 심긴 지시를 따라 쓴다 (experiment.md S1) |
| 공격에 쓰이는 에이전트 | 침입자가 돌리는 에이전트, 회사가 스스로 돌리는 레드팀 에이전트 |

- 길목에서는 셋을 구분할 수 없다. 모두 유효한 자격 증명을 가진 세션이다. 그래서 의도를 추측하지 않고, 어느 세션이든 할 수 있는 일의 크기를 묶고 한 일을 남긴다. 네 단이 그대로 그 수단이다.
- 레드팀 에이전트도 같은 길을 지난다. 허가받은 공격이라도 운영 데이터를 실제로 지우면 안 되므로 같은 한도와 기록을 받는다.

공격자를 대상에 넣으면 실수만 볼 때의 가정 다섯이 깨진다.

| 실수만 볼 때 | 공격자도 볼 때 |
|---|---|
| 한도는 문장마다 본다 | 한도 아래로 쪼개 보낸다. 신원별로 누적해서 봐야 한다 |
| 판단이 실패하면 통과시켜도 된다 | 실패를 일부러 일으킨다 (S8). 실패하면 막아야 한다 |
| 자격 증명을 잘못 주는 것은 운영 실수다 (5장) | 주된 공격 경로다 |
| 문장 모양으로 캐시한 판정은 부정확할 뿐이다 | 우회로다. 무해한 값으로 통과받은 모양에 다른 값을 넣는다 |
| 틀린 쓰기는 되돌리면 된다 | 읽어 간 것은 되돌릴 수 없다 |

- 넷째 줄은 6장의 기록에서 나온 추론이다. hoop을 직접 돌려 확인하지 않았다. 3번 단계의 벤치마크에서 잰다(10장).

**첫 출시의 설계 대상은 실수하는 에이전트다**(D30). 공격자 대응 가운데 나중에 고치기 비싼 둘만 지금 넣는다.

- enforce에서는 실패하면 막는 것이 기본값이다.
- 영향 한도는 문장별 한도와 함께 접속 계정별 누적 한도를 둔다. 연결 단위로 세면 다시 접속해서 초기화할 수 있다.

"보안 제품"이라는 주장은 6번 단계(TLS, 접속 계정 기반 신원, 자격 증명 보관)를 마친 뒤에 한다. 그 전까지 보안을 주장하는 근거는 D21 그대로 결정론적 통제뿐이다.

**사람의 주의는 한정된 자원이다**(D31)

에이전트를 믿고 확인하지 않게 된 사람이 Stet의 보류 건은 계속 확인할 것이라고 가정할 수 없다(4장의 93%). 그래서 사람에게 올리는 양을 설계 대상으로 둔다. 무엇을 올릴지는 세 가지를 함께 보고 정하고, 셋 다 네 단에서 나온다.

| 보는 것 | 나오는 곳 | 예 |
|---|---|---|
| 불확실성 | 3단의 confidence | 모델이 확신하지 못한 중복 |
| 영향 | 1단의 측정 | 테이블의 24%를 건드리는 쓰기 |
| 되돌릴 수 있는 정도 | 2단의 쓰기 전 값 | 되돌릴 수 있는 한 행 수정, 되돌릴 수 없는 읽기 |

- 낮은 confidence를 전부 사람에게 넘기는 것으로는 부족하다. 영향이 크면 모델이 확신해도 사람이 봐야 한다. 작고 되돌릴 수 있으면 확신이 낮아도 통과시키고 표시만 해 둘 수 있다.
- 지금의 verdict 정책은 이 셋을 따로 본다(spec-v0.1 6장). 함께 보는 정책은 설계하지 않았다.
- 사람에게 올리기 전에 더 강한 모델이 한 번 더 볼 수 있다. 실험에서 Jev가 올린 89건을 Opus 5.5가 다시 보자 50건이 남았고, 50건 모두 실제 결함이었다(lab.md "arm D 결과"). 합성 데이터이고 사전 등록된 판정이 아니다.

사람이 실제로 개입할 수 있으려면 넷이 필요하다.

| 약속 | 지금 |
|---|---|
| 올라온 이유, 영향, 근거를 짧게 볼 수 있다 | reason과 상태는 `stet.decisions`에 남는다. 보여 주는 화면은 없다 |
| 자동으로 통과한 것도 표본으로 다시 본다 | 라벨 컬럼이 있다. 표본을 뽑는 방법은 없다 |
| 검토가 밀리거나 담당자가 없을 때의 처리가 정해져 있다 | 정하지 않았다 |
| 승인한 뒤 데이터가 바뀌었으면 그 승인으로 실행하지 않는다 | v0.1 스펙에 설계가 있다(승인 시 버전 확인). 구현은 없다 |

**사람이 보는 단위는 업무다**(D31)

| 단위 | 쓰는 곳 | 근거 |
|---|---|---|
| 질의 | 실행 여부와 영향의 통제 | Stet이 직접 본다 |
| 접속 계정 | 권한, 누적 한도 | DB가 인증한다 |
| 세션 | 읽기와 쓰기의 이력(4단) | Stet이 직접 본다 |
| 업무 | 사람이 목적, 변경, 결과를 묶어 본다 | 에이전트가 스스로 적는다 |

- 사람은 "이 연결에서 어떤 문장이 실행됐나"가 아니라 "누구에게 맡긴 어떤 일이 무엇을 바꿨나"로 이해한다.
- 업무 이름과 `on_behalf_of`는 스스로 적는 값이다. 묶어서 보여 주는 데만 쓰고, 한도와 권한은 접속 계정에 건다.
- 연결 풀을 쓰면 한 연결이 여러 업무에 쓰이고 한 업무가 여러 연결에 걸친다. 그래서 되돌리기의 단위를 세션으로만 두면 부족하다(9장 4번).
- Stet이 문장만 보고 업무의 목적을 알아낸다고 약속하지 않는다.

## 8. 구조

쓰기 한 건의 흐름이다. `[exists]`는 지금 있는 것, `[extend]`는 고칠 것, `[new]`는 새로 만들 것이다.

```
 agent write
     │
 1 Classify   sqlparse          pass │ single-row │ multi-row │ forbidden     [extend]
     │                            └──> relayed as-is
 2 Measure    gate              ask the DB: rows hit, share of table,
     │                          cascade reach                                 [new]
 3 Rules      decide            forbidden -> reject
     │                          over the impact limit -> hold
     │                          stale read -> reject                          [extend]
     │                            └──> settled here: skip 4
 4 Judge      decide + adapter  value-level questions to Jev,
     │                          single-row writes only                        [exists]
 5 Verdict    decide.Verdict    commit │ hold │ escalate │ reject             [exists]
     │
 6 Act        proxy             commit -> forward unchanged
     │                          else   -> error to the agent, not forwarded   [new]
 7 Record     store             decision + values before the write            [extend]
```

- 결정론이 먼저다. 3번에서 끝나는 쓰기는 모델을 부르지 않는다. 모델 호출 수와 지연이 함께 줄어든다.
- 섀도 모드는 6번만 다르다. 나머지를 그대로 계산·기록하고 6번은 항상 통과시킨다.
- 다중 행 쓰기는 처음에는 영향 측정만 받는다. 행마다 값 단위로 판단하는 것은 뒤로 미룬다.
- 읽기는 이 흐름을 타지 않는다. 1번 단계에서는 게이트 대상 테이블을 읽는 문장의 결과 행 수만 기록하고 판정하지 않는다(7장).
- 2번 단계까지는 hold, escalate, reject가 모두 에이전트에게 에러로 돌아간다. 사람에게 가는 길은 2b에서 생긴다(9장).
- CLAUDE.md의 규칙 일곱 개는 그대로 지킨다. enforce에서 모델은 쓰기를 보내기 전에 불리는데, 판단 대상이 autocommit 단일 문장이라 그 시점에 열린 트랜잭션이 없다(규칙 1).

| 패키지 | 바뀌는 것 | 단계 |
|---|---|---|
| `internal/sqlparse` | 다중 행 쓰기를 조건절과 함께 분류(1). 게이트 대상 테이블의 DDL·`TRUNCATE`를 금지 형태로 분류(2) | 1, 2 |
| `internal/gate` | 영향 측정 질의. enforce에서는 쓰기 전에 판단까지 마친다 | 1, 2 |
| `internal/decide` | verdict 앞에 결정론 단계(영향 한도, 낡은 읽기) | 1, 5 |
| `internal/config` | 테이블별 영향 한도(문장별, 접속 계정별 누적), enforce 설정 검증, 에이전트 역할 | 1, 2 |
| `internal/proxy` | 게이트가 "보내지 마라"를 돌려줄 수 있게 인터페이스 변경. 문장을 버리고 에러를 대신 응답. 세션별 읽기 추적 | 2, 5 |
| `internal/store` | 영향 기록, 쓰기 전 값 저장, 복구 함수 | 1, 4 |
| `internal/lab` | 모양은 같고 영향이 다른 쓰기 세트, hoop 실행기, 채점 | 3 |

가장 위험한 변경은 프록시다. 지금은 메시지를 보기만 하고 무조건 넘긴다. 막으려면 문장을 버리고 프록시가 직접 에러를 만들어 응답해야 하고, 확장 프로토콜에서는 이미 넘어간 Parse·Bind와 순서를 맞춰야 한다.

## 9. 순서

| # | 단계 | 만드는 것 | 이 자리에 오는 이유 |
|---|---|---|---|
| 0 | 정리 | 진행 중인 hard negative 실험(D28) 마무리, 방향 기록(이 문서, D29) | hard negative 세트가 3번의 재료다 |
| 1 | 영향 측정 (섀도) | 다중 행 쓰기를 분류하고 영향을 DB에 물어 기록. 게이트 대상 테이블을 읽는 문장의 결과 행 수 기록. 한도는 문장별과 접속 계정별 누적 | 아무것도 막지 않아 작고, 2번의 전제다 |
| 2 | enforce 최소형 | verdict에 따라 실제로 막고 이유를 돌려준다. 실패하면 막는 것이 기본값이다. 에이전트 역할만 Stet을 거치게 한다 | 1번 없이 켜면 다중 행 쓰기를 전부 거부하거나 전부 통과시킬 수밖에 없다 |
| 2b | 사람의 최소 경로 | 보류 건을 근거와 함께 보고 승인하거나 거부한다(v0.1 스펙의 `stet.approve` / `stet.reject`). 승인할 때 행 버전을 다시 확인한다. 화면은 만들지 않는다 | 이것이 없으면 hold와 escalate가 reject와 구분되지 않는다 |
| 3 | hoop 대비 벤치마크 | 같은 쓰기 스트림을 양쪽에 돌려 채점. 공격 세트를 포함한다(10장) | 막을 수 있어야 통제 제품끼리의 비교가 된다 |
| 4 | 되돌리기 | 영향받은 행 전체의 쓰기 전 값 저장, 세션 단위 복구 | 3번에서 방향이 확인된 뒤에 투자한다 |
| 5 | 낡은 쓰기 탐지 | 세션이 읽은 시점과 쓸 때의 행 버전 비교 | 프록시의 읽기 추적이 필요해 가장 깊은 변경이다 |
| 6 | 내놓기 전 숙제 | TLS, DB 역할 기반 신원(매니지드 Postgres용 자격 증명 보관 포함), 가용성 | 외부 사용자가 생기면 앞당긴다. "보안 제품"이라는 주장은 이 단계 뒤에 한다 |
| 7 | 넓이 | hoop이 가진 기능 전부: 검토 화면과 알림, 마스킹, 컨트롤 플레인, 다른 프로토콜. 이어서 다른 데이터 플랫폼(12장) | 아래 참고 |
| 8 | 품질 | 버전을 아는 캐시, 세션 기록에서 나온 힌트 | 통제가 자리 잡은 뒤다(12장) |

- 1번의 읽기 기록과 누적 한도, 2번의 실패 시 차단, 3번의 공격 세트, 8번은 D30으로 더해졌다. 읽기 기록과 누적 한도는 스펙 1(spec-v0.2-impact.md)에 아직 설계가 없다.
- 값 단위 판단(3단)은 이미 있어서 별도 단계가 없다. 2번에서 쓰기 전에 판단하는 동기 경로로 들어간다.
- 2번의 "최소형"은 막기와 에러 반환까지다. 보류 건의 승인·거부와 실행 직전의 행 버전 재확인은 2b에서 한다.
- 2b는 D31로 더해졌다. 승인·거부의 최소 경로만 앞당긴다. 검토 화면과 컨트롤 플레인은 7번에 그대로 둔다.
- **7번은 "할지 말지"가 아니라 "언제"의 문제다.** hoop의 기능은 실제 고객이 겪는 문제이고, hoop이 그것부터 푼 이유도 그래서일 가능성이 높다. 깊이를 먼저 만들고 넓이는 향후에 모두 구현한다. 7번 안의 순서는 첫 사용자를 보고 정한다.

## 10. 증명: hoop 대비 벤치마크

모양 기반 판정이 구조상 점수를 내지 못하는 세트로 비교한다.

- 모양은 같고 영향이 다른 쓰기
- 값 단위 결함 (기존 F1~F4)
- 정상 쓰기를 막는 비율 (hard negative, D28)
- 공격 세트: experiment.md의 S4(대량·파괴 쓰기), S5(분류기 우회), S8(실패 유도)에 둘을 더한다
  - 쪼개기: 한도를 넘는 쓰기를 한도 아래의 여러 문장으로 나눠 보낸다
  - 모양 재사용: 무해한 값으로 통과받은 문장 모양에 다른 값을 넣어 다시 보낸다

hoop의 배포 바이너리와 Stet을 같은 스트림에 돌린다. hoop에는 가장 잘 나오는 설정을 준다. 기준은 실험 때처럼 결과 전에 고정한다. hoop이 예상보다 잘 나오면 그것도 결과로 적는다.

공격 세트는 운영 DB에 돌리지 않는다. 섀도 모드는 아무것도 막지 않으므로(규칙 6) 공격 쓰기가 그대로 실행된다. 복제본이나 녹화의 재생에 돌린다. 같은 세트를 고객 데이터의 복제본에 돌리면 도입 전 진단으로 쓸 수 있다. 제품으로 만들지는 정하지 않았다.

**위임을 감당하는가**(D31)

위의 비교는 판단 엔진의 성능을 잰다. 제품의 목적은 위임이므로 다음도 잰다. 자동 통과율과 사람 개입 감소만 올리면 위험을 놓치므로, 결과의 품질과 함께 본다.

| 지표 | 잴 수 있는 때 |
|---|---|
| 정상 쓰기가 막히는 비율 | 지금 (false hold) |
| 사람에게 올라가는 건수 | 지금 (escalate 수) |
| 자동 통과한 것 가운데 놓친 결함 | 지금은 합성 데이터에서. 실제 데이터에서는 2b 뒤의 표본 검토로 |
| 사람의 개입 없이 끝난 업무의 비율, 막힌 뒤 포기한 업무의 비율 | 2번 뒤. 에이전트를 붙여 다시 녹화한다 |
| 문제를 추적하고 멈추고 되돌리는 데 걸리는 시간 | 4번 뒤 |
| 업무당 사람이 검토에 쓰는 시간 | 실제 검토자가 있어야 한다. 합성 실험으로는 못 잰다 |
| 섀도에서 enforce로 넘어가는 비율 | 실제 사용자가 있어야 한다 (D10의 PMF 지표) |

## 11. 열린 질문과 위험

| 질문 | 현재 생각 |
|---|---|
| 저가 모델 에이전트는 얼마나 틀리나 | 재지 않았다. 같은 업무를 Haiku 에이전트로 다시 녹화하면 자연 결함률이 나온다. 낮게 나오면 3단의 근거가 더 약해진다 |
| 낡은 쓰기는 실제로 얼마나 자주 나나 | 읽은 범위에서는 어느 논문도 현장 빈도를 재지 않았다. 4장의 식은 추정이다 |
| 소형 로컬 LLM이 값 단위 판단에서 Jev에 얼마나 가까운가 | 모른다. 가까우면 Jev 의존과 데이터 반출 문제를 함께 푸는 길이 된다. 멀면 "값 단위 판단에는 판단형 모델이 필요하다"는 근거가 된다 |
| 데이터 반출 | 판단하려면 데이터를 외부 API(Jev)로 보내야 한다. 위험 때문에 도입하는 레이어에서 큰 약점이다 |
| 틀린 쓰기가 곧 사고인 첫 데이터 영역 | 정하지 않았다. 수신 동의, 금액, 재고, 권한 필드가 후보다 |
| hoop이 값 단위로 내려오면 | 모양 캐시를 포기하고 쓰기마다 모델을 불러야 한다. 따라오려면 구조를 바꿔야 하지만 속도가 빠른 팀이다 |
| DB 업체의 흡수 | 가장 큰 위험이다. 여러 DB 위에 얹을 수 있다는 중립성이 방어선이다 |
| 운영 DB 앞에 서는 부담 | 에이전트 전용 길목이라 서비스에는 영향이 없다. 그래도 에이전트 경로의 가용성은 책임져야 한다 |
| 읽기를 어디까지 다룰 것인가 | 기록, 한도, 마스킹 순으로 본다. 읽기는 쓰기보다 훨씬 많아서 문장마다 기록하면 비용이 크다. 접속 계정별 집계로 충분한지 정해야 한다 |
| 누적 한도의 창과 대상 | 접속 계정 기준으로 센다는 것만 정했다. 창의 길이는 정하지 않았다. 쪼개기를 막으려면 단일 행 쓰기도 함께 세야 한다 |
| 넓힌 자리의 기존 업체 | 데이터 접근 거버넌스 업체(Immuta, Satori 등)가 웨어하우스 앞에 이미 있다. 에이전트를 어떻게 다루는지는 확인하지 않았다. landscape.md에 조사를 더해야 한다 |
| "에이전틱 쿼리"라는 이름 | 검색·RAG 쪽에서 비슷한 말을 다른 뜻으로 쓰는지 확인하지 않았다 |
| 위임이 DB 길목을 지나는가 | 전략 가설의 가장 약한 고리다. 에이전트가 앱 API나 MCP 도구만 쓰고 그 서비스가 서비스 계정으로 붙으면 Stet은 보지 못한다. 회사의 거버넌스가 규칙으로 정할 일이다(5장). 실제로 어떻게 붙이는지는 첫 고객 대화에서 묻는다 |
| 규칙이 지켜지는지 보여 주기 | Stet을 거치지 않고 게이트 대상 테이블에 쓰는 접속을 DB에 물어 보고하는 것. 방법은 설계하지 않았다 |
| 사람에게 올리는 양 | 검토자가 감당할 양을 넘으면 그대로 승인하게 된다. 목표 숫자와, 검토가 밀릴 때의 처리를 정하지 않았다 |
| 승인도 공격면이다 | 보류를 쏟아내 검토자를 지치게 한 뒤 하나를 통과시킬 수 있다. D30에 따라 지금은 적어만 둔다 |
| 오픈 코어 경계 | D9는 검토 UI와 감사 대시보드를 유료에 둔다. 사람의 감독이 제품의 목적이 되면 오픈소스에 남길 최소 경로를 정해야 한다. 2b의 승인·거부 함수는 v0.1 스펙대로 코어에 둔다 |

## 12. 목적지: 모든 데이터 플랫폼 앞단, 그리고 품질

9장의 7번과 8번이 향하는 곳이다. 순서는 바꾸지 않는다. 지금 만드는 것이 어디로 가는지를 적어 둔다.

**다른 데이터 플랫폼**

"문장을 보고 추측하지 않고 엔진에 물어본다"는 원리는 그대로 옮겨진다. 구현은 엔진마다 새로 만든다.

| | Postgres (지금) | 웨어하우스 (목적지) |
|---|---|---|
| 주된 질의 | 쓰기 | 주로 읽기 (분석 에이전트) |
| 주된 위험 | 오염, 파괴 | 유출, 비용 |
| 실행 전에 묻는 것 | 걸리는 행 수, 외래 키 연쇄 | 스캔량 추정 |
| 서는 곳 | pgwire 프록시 | 엔진마다 다른 HTTP API 앞. pgwire 같은 공통 와이어가 없다 |

- 여러 엔진 위에 서는 중립성은 11장에서 DB 업체의 흡수에 대한 방어선으로 든 것과 같다.
- 넓힌 자리는 비어 있지 않다(11장).

**품질**

통제는 강제해야 깔리고, 품질은 에이전트가 원해서 쓴다. 같은 길목에서 둘을 함께 주면 에이전트를 만드는 쪽에도 Stet을 거칠 이유가 생긴다. 이 자리에서만 할 수 있는 것부터 한다.

| 기능 | 이 자리여야 하는 이유 | 단계 |
|---|---|---|
| 막은 이유를 구조화해서 돌려주기 (`duplicate:4812`) | 이유가 DB 상태에서 나온다. 에이전트는 DB 에러보다 고칠 근거를 더 받는다 | 2번에 이미 있다 |
| 버전을 아는 캐시 | 일반 캐시는 읽기와 쓰기 사이를 벌려 낡은 쓰기를 늘린다. 4단이 있으면 캐시가 낡았는지 안다 | 5번 뒤 |
| 세션 기록에서 나온 힌트 | 어느 질의가 막혔고 되돌려졌는지는 이 기록에만 있다 | 미정 |

- 온톨로지와 시맨틱 레이어는 직접 만들지 않는다. 3장의 표대로 대형 업체가 메우고 있고, 모델이 좋아질수록 줄어드는 갭이다. 필요해지면 있는 것을 입력으로 받는다.
